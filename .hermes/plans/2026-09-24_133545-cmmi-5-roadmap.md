## 1. What's still true

### Foundation layer (existing)

- **Hardware:** NVIDIA RTX 5070 Max-Q (CUDA0, ~8 GB VRAM) + NVIDIA RTX 5070 (Vulkan1) + Intel ARL (Vulkan0, ~23 GB shared).
- **Model registry:** `context-verification/*.json` is the 22-model source of truth; `llama-swap/config.yaml` is the **6-model** llama-swap config (the two are different things).
- **Configuration format:** `llama-swap/config.yaml` uses a `name: llama.cpp configuration, version: 1.0.0, schema: v1` YAML envelope with top-level `models:` (a list of `- name/provider/model/roles/capabilities`) and `context:` provider blocks. This is **not** the flat `models: <name>: cmd: ... macros: ...` shape the old roadmap assumed. See `docs/llama-swap.md` and `docs/monorepo.md`.
- **Operational layers that exist:**
  - `llm_manager/` — Flask app + FastAPI docs; hardware-aware profile generation; model discovery (JSON metadata + on-disk scan); config/tuning persistence and export; ORM + SQLite.
  - `nix/` — treefmt-nix + blueprint flake (x86_64-linux only), devshell, pre-commit hooks, CI (`.github/workflows/nix-check.yml`).
  - `scripts/check-md-links.py` — markdown link checker wired into the pre-commit config.
- **Performance targets** (still valid — recorded in `docs/llama-swap.md`, `.agents/config.json`, and `SKILL.md`):

| Metric | Target | Acceptable |
|--------|--------|------------|
| Model swap time | < 2s | < 5s |
| Model load time | < 5s | < 10s |
| Generation speed (7B) | > 10 t/s | > 5 t/s |
| VRAM utilization | < 70% | < 90% |
| Context efficiency | > 80% | > 50% |

### This plan's biggest problem: it's a hard-copy of the 2026-09-24 assumptions

Every phase referenced by name/stub was written before the monorepo was reorganized. The plan:

- Claims **29 model definitions** in `config.yaml` → **false**; `config.yaml` has **6** models. The **22** figure belongs to `context-verification/*.json`.
- Claims the plan file lives side-by-side with `benchmark_results.json`, `VERSIONS.md`, `KNOWN_ISSUES.md`, etc. → **none of those files exist in the repo**.
- Claims `llama-swap/run_benchmarks.py` should be rewritten with a full benchmark runner → **`run_benchmarks.py` is still a placeholder** with `TODO: User will implement custom benchmarking approach.`.
- Targets **CMMI Level 5 (self-optimizing, predictive modeling)** → unrealistic for a user-specific local-inference config repo on an 8 GB GPU. Realistically this repo tops out at **CMMI Level 2 (repeatable)**.
- Contains **hardcoded `/home/waflores/` paths** throughout (all the Python scripts and JSON artifacts).

**Recommendation: keep this file as a strategic guide, re-scope the target to CMMI Level 2, fix the hardpaths, and re-baseline the model counts. Do not execute it as written.**

## 4. What to do about each phase

### Phase 1 — Foundation measurement (still the priority)

**Goal:** Produce the first real benchmark results and the measurement pipeline, and retire the placeholder.

**Deliverables:**

- `llama-swap/run_benchmarks.py` → replace the placeholder with a real, idempotent benchmark driver:
  - Reads models from `llama-swap/config.yaml` (not a hardcoded list).
  - Starts/stops `llama-swap` if the health endpoint (`http://127.0.0.1:10001/health`) is down.
  - For each model: load time, VRAM usage, unload time, raw GPU utilization if available.
  - Emits a normalized JSON results file with timestamps, config hash, and targets crossed.
- `benchmark_results.json` (at repo root or `logs/benchmark/`) — normalized results with a clear schema, not just a hand-written stub.
- `logs/benchmark/` — per-model JSON files (one per run).
- `NIX format` and `ruff check --check` pass (already wired into pre-commit and CI).
- `docs/llama-swap.md` and `docs/monorepo.md` references updated to point at the real benchmark pipeline.

**Tooling decision (from the benchmarking report):** adopt a standard tool (`llama-bench` / `llama-benchy` / llama.cpp `llama-bench`) or a thin wrapper around it. The repo currently has **zero** committed benchmark results; this is the heaviest gap. The placeholder scripts (`run_benchmarks.py`, `run_llama_bench.sh`) must be deprecated or replaced, not left alongside a new pipeline.

**Acceptance criteria:**

- `[ ]` `python3 llama-swap/run_benchmarks.py --all` exits 0 and writes a valid JSON results file with 1+ models.
- `[ ]` Results include per-model load time, unload time, and inference tokens/s.
- `[ ]` `nix flake check` and `nix fmt` still pass (CI green).
- `[ ]` `docs/llama-swap.md` and `SKILL.md` reference the new pipeline, not the placeholders.

### Phase 2 — Error tracking & troubleshooting (still relevant, but de-emphasize)

**Goal:** Only if the first benchmark runs actually surface errors. Keep it low-cost:

- `logs/errors.json` — structured error log with timestamps and stack traces (or the plan's `KNOWN_ISSUES.md`/TROUBLESHOOTING.md, whichever matches the team's preference). The plan's `KNOWN_ISSUES.md` and `TROUBLESHOOTING.md` are good docs to have, but only populate them with **real** issues found during benchmarking, not with placeholders.
- No further work until the Phase 1 artifacts exist and the first benchmark run has completed.

### Phase 3 — Automated validation (still valid; fold into `llm_manager`)

The plan's `config_validator.py` and `update-config.sh` are well-scoped but their hardcoded paths make them non-portable. Fold the **validation** idea into the existing `llm_manager` package (which already has tests, config generation, and hardware-aware profiling) and expose it as a CLI flag, rather than maintaining a duplicate script in `llama-swap/`.

**Deliverables:**

- A `--validate` mode in `llm_manager` (or a small wrapper in `scripts/`) that checks: config syntax, model file existence, device assignments, `globalTTL`/`healthCheckTimeout` presence, and the health endpoint.
- Reuse `context-verification/*.json` (already the source of truth) as the validation metadata, not a separate file.
- `logs/validation.json` — structured validation output.

**Acceptance criteria:**

- `[ ]` `uv run python -m llm_manager` (or a `scripts/validate.py` wrapper) exits 0 and reports warnings for the current config (e.g., globalTTL, healthCheckTimeout) as informational, not failure.
- `[ ]` The 22-model registry and the 6-model config are validated independently.
- `[ ]` No hardcoded `/home/waflores/` paths in new/updated scripts.

### Phase 4 — Performance tracking (defer / low priority)

**Goal:** A lightweight performance logger. This is baseline-of-the-art in ops but the repo doesn't have a dedicated observability team right now. Start with:

- A small `performance_logger.py` in `llama-swap/` that appends structured JSON entries (`load`, `unload`, `swap`, `inference`, `error`) to `logs/performance.json`, with `get_stats()` for quick look at averages.
- Keep the last N entries (e.g., 500), don't keep growing forever.

**Acceptance criteria:**

- `[ ]` `uv run python -m llm_manager.performance_logger --action stats` prints a valid JSON summary.
- `[ ]` No hardcoded paths.

### Phase 5 — Automation & optimization (future optional)

**CMMI Level 5 (self-optimizing, predictive modeling) is out of scope** for this repo. If the team later wants it, the natural next step after Phases 1–4 is:

- An optimization engine that reads `benchmark_results.json` + `performance_logs.json` and proposes config changes (quantization, context cap, device assignment).
- Predictive modeling of load/swap time from model size × VRAM — a single model + a few measurements is not enough signal to justify it now.

## 6. Risks, tradeoffs, and open questions

### Risks

- **Benchmarking is slow on 8 GB VRAM.** Loading large models (24B, 27B) may fail or require swapping. Mitigate: benchmark by context size, not by loading every model fully; use `-ngl`/`flash-attn` sparingly; record OOM as a data point, not a failure.
- **Tool fragmentation.** If we keep `run_benchmarks.py` and adopt a standard tool (llama-bench), we'll end up with two result formats. **Decision:** pick **one canonical output format** and have the other wrap/aggregate it.
- **Hardcoded paths.** Any script written with `/home/waflores/` will break portability. **Decision:** always read paths from env vars or use relative paths.

### Tradeoffs

- **Manual vs. automated optimization.** Start manual (recommended by the old plan); add automation only after we have enough benchmark data to validate a heuristic.
- **Comprehensive vs. minimal benchmarking.** Start minimal (load/unload + a short completion pass per model); add context-size sweeps later.

### Open questions (to resolve this sprint)

1. **Benchmark tool?** Adopt `llama-bench` (industry standard, actively maintained) or keep a thin hand-rolled driver. **Decision needed.**
2. **Where do results live?** Repo root (`benchmark_results.json`) vs `logs/benchmark/` vs `context-verification/`. **Decision needed.**
3. **CI integration?** The old plan said "benchmarking in CI, optional initially." Decided: **no heavy CI benchmarks** (they're slow and non-deterministic); keep benchmarking local-only, with `check-md-links.py`-style lints for docs that reference the benchmark pipeline.
4. **CMMI target?** Confirm **Level 2** (not Level 5) for this scope.
5. **`context-verification` vs `config.yaml` numbering?** Document the 22 / 6 split clearly so future plans don't repeat this error.
